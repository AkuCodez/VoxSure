# VoxSure: an error-aware, multilingual voice assistant for student support

**Live application:** _not deployed yet: add the URL after deployment (see `docs/DEPLOYMENT.md`)_  
**Source code:** https://github.com/AkuCodez/VoxSure  
**Colab training notebook:** `ml/notebooks/VoxSure_Train_Colab.ipynb`

Every figure below is generated by `ml/scripts/build_report.py` from result files written by reproducible runs (`ml/reports/*.json`, seed 42). Nothing is typed in by hand.

## 1. Abstract

VoxSure is a browser voice assistant for a bounded Student Support & Campus Information domain. Speech is transcribed with Whisper (`faster-whisper`), the transcript is shown with doubtful words underlined and can be edited, and a fine-tuned DistilBERT classifier predicts one of 15 intents plus an explicit out-of-scope class. A recovery policy then decides to **answer** from a reviewed knowledge base, **ask a targeted clarification**, or **fall back transparently**, instead of always guessing. On a held-out test set the policy reduced the rate of confidently wrong answers from 24.9% (always answer) to 4.4%, at the cost of asking for clarification on 33.1% of turns. The system replies in the user's language (Hindi, Punjabi and German were measured; others are best effort) and, if an AI provider is configured, can answer non-campus questions with clearly labelled AI-generated replies. The dataset is small and author-written, so absolute numbers are optimistic relative to real users; see Limitations.

## 2. Problem and related work

Misrecognised words and ambiguous requests cause voice assistants to give confident but irrelevant answers. Relevant prior work: Whisper for robust ASR (Radford et al., 2022); DistilBERT, a compact distilled transformer (Sanh et al., 2019); out-of-scope intent detection datasets such as CLINC150 (Larson et al., 2019); over-confidence of modern networks and temperature scaling (Guo et al., 2017); and NLLB-200 for translation across 200 languages (NLLB Team, 2022). Uncertainty-aware intent clarification already exists in the literature, so the contribution claimed here is narrower: a **reproducible, measured evaluation of a recovery workflow** (transcript editing, uncertainty and ambiguity handling, targeted clarification, optional consent-based correction memory) in one defined domain, compared against a no-clarification baseline, plus an honest multilingual extension.

## 3. Dataset

* **Source:** all 340 seed utterances were written by the author for this project (no scraped or third-party data). Seeds were expanded programmatically with conversational fillers, ASR-style normalisation and plausible ASR substitutions (e.g. "hostel"→"hostile"). Script: `ml/scripts/build_dataset.py`.
* **Classes (16):** about_bot, academic_calendar, campus_services, certificates, exam_info, fee_payment, greeting, help_capabilities, hostel_info, it_helpdesk, library_borrow, library_hours, out_of_scope, placement_process, scholarship_aid, thanks_bye.
* **Splits** (by seed group within each class, so variants of one seed never straddle splits; zero exact-text overlap): train 1582, validation 337, test 337. Fixed seed 42.
* **Ambiguous set (evaluation only, never trained on):** 50 hand-written under-specified requests; 25 for policy tuning, 25 held out for test.
* **Dataset history (disclosed):** version 1 had 13 classes. (2) `about_bot` and `help_capabilities` were added after manual testing showed "What's your name?" fell into the out-of-scope fallback. (3) A run showed `thanks_bye` with F1 = 0.00 on test (only 12 seeds), so more small-talk seeds were added. (4) More varied seeds were added for weak classes (campus services, hostel, IT, scholarship, fees, exams) and the test set enlarged. Each change regenerated the splits and all results; metrics from earlier versions are superseded and not reported. This is a mild form of test-set feedback.
* **Knowledge base:** answers use illustrative values for a fictional campus (not real institutional data). Each answer carries a source label and a real last-updated date; no links are shown because none exist for an illustrative campus.

## 4. Models and method

| Component | Choice |
|---|---|
| ASR | `faster-whisper` `small` (multilingual, int8, CPU), VAD filter, per-word probabilities; auto language detection or user-selected language |
| Intent classifier | `distilbert-base-uncased` fine-tuned, 16 classes, max length 48, AdamW lr 5e-05, batch 16, 6 epochs, seed 42, best epoch by validation accuracy (82.2%) |
| Confidence | Softmax with temperature scaling, T = 1.04 fitted on validation data only |
| Baseline | TF-IDF (1-2 grams) + Logistic Regression (experimental baseline only) |
| Policy | answer threshold 0.80, margin 0.50, low-confidence threshold 0.15, out-of-scope threshold 0.40; grid-searched on **validation + ambiguous_val only**, then frozen before test evaluation |
| Translation | NLLB-200 distilled 600M (int8, CTranslate2): non-English input → English → classifier. Hindi, Punjabi and German replies are hand-written; other languages use NLLB with a numeric-consistency guard |
| Open-domain answers | Optional external AI provider (Claude or any OpenAI-compatible service) for questions the classifier marks out-of-scope; labelled AI-generated; user opt-out; daily cap |

Policy objective on validation: reward correct answers/fallbacks and appropriate clarifications (0.6), penalise a wrong answer 3× and an unnecessary clarification 0.6×. A "wrong answer" is (a) answering with the wrong intent, (b) answering an out-of-scope request (with the AI provider off), or (c) answering an ambiguous request at all.

## 5. Results

### 5.1 Experiment A: text-only intent classification (test, n = 337)

| Model | Accuracy | Macro-F1 (95% bootstrap CI) |
|---|---|---|
| TF-IDF + LogReg baseline | 0.519 | 0.502 (0.450 – 0.542) |
| Fine-tuned DistilBERT | 0.795 | **0.795** (0.749 – 0.834) |

The two intervals do not overlap, so the gap over the baseline is not a resampling artefact. Per-class test F1 (DistilBERT): library_borrow 1.00, placement_process 1.00, library_hours 0.96, out_of_scope 0.96, thanks_bye 0.95, fee_payment 0.95, greeting 0.93, scholarship_aid 0.93, help_capabilities 0.80, certificates 0.78, hostel_info 0.78, about_bot 0.73, campus_services 0.60, it_helpdesk 0.48, exam_info 0.46, academic_calendar 0.42. Confusion matrix: `ml/reports/confusion_matrix.png` and the dashboard.

Weakest classes: **academic_calendar** (0.42, 14 test items); **exam_info** (0.46, 28 test items); **it_helpdesk** (0.48, 28 test items). Each class has few distinct held-out phrasings, so single-class scores are high-variance, and earlier dataset versions of the same pipeline scored noticeably differently, so **differences of several points should be treated as noise**.

**Calibration.** ECE on test: 0.059 uncalibrated vs 0.058 after temperature scaling; mean test confidence 80.4% vs accuracy 79.5%. Confidence drives decisions, so thresholds are tuned empirically rather than trusting raw probabilities.

### 5.2 Experiments B vs C: no recovery vs error-aware recovery (test n = 362 = 337 clear + 25 ambiguous)

| Metric | B: always answer | C: error-aware |
|---|---|---|
| Wrong-answer rate, all turns (95% CI) | 24.9% (20.7% – 29.0%) | **4.4%** (2.5% – 6.4%) |
| Clarification rate | 0.0% | 33.1% (28.2% – 38.4%) |
| Wrong-answer rate, clear requests only | 19.9% | 2.1% |
| Task completion in one turn (clear requests) | 79.5% | 65.9% |
| Task completion if the user taps a clarification option | 79.5% | 76.0% |
| Ambiguous requests answered (wrongly) | 23/25 | 9/25 (14 clarified) |

The reduction in wrong-answer rate is 16.6% – 24.9% (95% CI). Trade-off: the policy asks an unnecessary clarification on 105 of 337 clear requests (31%), and even counting a tap on an offered option it completes fewer tasks than the baseline (76.0% vs 79.5%). Whether this trade is right depends on the cost of a wrong answer versus an extra question; thresholds should be re-tuned with real users.

### 5.3 Experiment E: noise stress (test text with heavier synthetic corruption)

Text-only accuracy on stressed clear requests: 67.1%. Wrong-answer rate: B 33.1% vs C 5.0%; clarification rate C 44.5%; one-turn completion B 67.1% vs C 51.3% (66.8% with an option tap). Under heavy corruption the policy is very conservative.

### 5.4 Speech pipeline

Whisper `small` on 76 synthetic test utterances (2 Windows text-to-speech voices); white noise added at the stated SNR.

| Condition | WER (domain prompt) | Latency p50 / p95 (s) | Wrong answers: always answer → VoxSure |
|---|---|---|---|
| Clean | 1.4% | 1.73 / 1.93 | 40.8% → 13.2% |
| SNR 20 dB | 1.7% | 1.88 / 4.15 | 42.1% → 13.2% |
| SNR 10 dB | 1.7% | 1.89 / 4.23 | 40.8% → 13.2% |
| SNR 5 dB | 3.3% | 1.83 / 4.19 | 42.1% → 13.2% |

On clean audio, WER without the domain prompt was 1.7% versus 1.4% with it. 
With automatic language detection (what the app does by default) on English audio, WER was 1.7% and the language was detected as English in 100.0% of clips.

**Caveats:** the audio is clean synthetic speech from two voices, so these figures say nothing about accents, spontaneous speech or real microphones: WER here is a lower bound. Latency was measured on the author's laptop CPU (int8, no GPU) while other jobs were also using the CPU, so it is pessimistic; an idle machine should be faster. Human recordings were not collected.

_No human recordings have been scored yet, so speech accuracy for Hindi, Punjabi and German is unmeasured (`ml/scripts/evaluate_human_recordings.py` is ready)._

### 5.5 Experiment D: correction memory (simulation)

Of 337 stressed utterances, 190 were not answered correctly on first pass and the corrected text was "remembered". When the same utterances recurred, the correct-answer rate was 43.6% without memory vs 57.0% with it. This is an **upper bound for exact repeats**: memory matches only the identical normalised utterance and does not generalise. No real-user study was done.

### 5.6 Multilingual (typed text → translation → classifier → reply)

47 sentences per language covering every intent plus out-of-scope, **written by the author and not verified by native speakers**; never used for training or tuning. English is the control. A language is labelled *verified* only if it met criteria fixed in advance: intent accuracy ≥ 80%, wrong-answer rate with recovery ≤ 10%, language-ID accuracy ≥ 95%.

| Language | Intent accuracy | Macro-F1 | Language ID | Wrong answers: always answer → VoxSure | Clarification | Translation p50 (s) | Label |
|---|---|---|---|---|---|---|---|
| English | 95.7% | 0.959 | 100.0% | 4.3% → 0.0% | 6.4% | 0.00 | verified |
| Hindi | 95.7% | 0.957 | 100.0% | 4.3% → 0.0% | 8.5% | 0.40 | verified |
| Punjabi | 91.5% | 0.910 | 100.0% | 6.4% → 0.0% | 12.8% | 0.34 | verified |
| German | 83.0% | 0.825 | 95.7% | 14.9% → 6.4% | 12.8% | 0.31 | verified |

**Reply side.** Raw machine translation changed a number in some fixed answers: hi: 0/4; pa: 0/4; de: 1/4; fr: 1/4; es: 1/4 (answers containing numbers). A Hindi example in testing turned a 9 am opening time into "night nine". For this reason Hindi, Punjabi and German replies are **hand-written** (also unverified by native speakers), and other languages use machine translation with a numeric-consistency guard that warns the user when a number changed. The guard only checks digits, so other translation errors are possible; an English original is always shown.

**Not measured:** speech recognition accuracy (WER) for Hindi, Punjabi and German, which needs human recordings; languages other than these four; romanised or mixed-language text.

### 5.7 Open-domain answers

Non-campus questions can be answered by an external AI provider (Claude or any OpenAI-compatible service). **No accuracy metric is reported for these answers**: they are not from the reviewed knowledge base, can be wrong, and are labelled as such. The integration (routing, opt-out, history, provider selection, failure fallback, daily cap, key loading) is covered by automated tests using stand-in providers and a local mock server; a call to a real provider has not been exercised in this repository because no key was available.

## 6. System and deployment

React + TypeScript + Tailwind frontend (live microphone waveform, per-word transcript highlighting, language badges, source labels, Pipeline insights panel, evaluation dashboard at `#/evaluation`); FastAPI backend with rate limiting and security headers; SQLite (default) or PostgreSQL for opt-in correction memory and metrics-only events; one Docker image serving both on a single HTTPS origin (`docs/ARCHITECTURE.md`, `docs/DEPLOYMENT.md`). Audio is never persisted and logged events contain no transcript text. The Docker image has **not been built** (Docker is unavailable on the development machine) and the app is **not deployed**.

Automated tests: backend (policy, every endpoint, multilingual flow, curated translations and numeric guard, general-answer routing and providers, failure paths, privacy, rate limiting) and frontend (components, evaluation page, axe accessibility audits). Counts are in the README.

## 7. Limitations and future work

* Author-written, templated dataset; test sentences come from the same author and distribution, so real-user accuracy is expected to be lower.
* Small test set with few distinct phrasings per class; results varied noticeably across dataset versions; intervals reflect resampling of this test set only.
* The weakest classes (academic_calendar, exam_info, it_helpdesk) need more diverse real utterances.
* 31% unnecessary clarifications on clear requests and lower one-turn completion than the baseline are a real usability cost; some ambiguous prompts are still answered confidently.
* ASR evaluated on synthetic English speech only. Needs human recordings across accents and noise, and any speech evaluation for Hindi, Punjabi and German.
* Multilingual test sentences and hand-written replies are not native-speaker verified; translation relies on English-trained models; other languages are best effort.
* AI-generated general answers are unmeasured and can be wrong; they involve sending text to an external provider (disclosed in the UI).
* Knowledge-base content is illustrative; browser speech synthesis availability varies, especially for non-English voices; correction memory is exact-match only.
* The dataset was revised several times after observing weak results (§3).
* Public deployment, the Docker build and real-microphone/real-provider checks remain to be done by the owner.
